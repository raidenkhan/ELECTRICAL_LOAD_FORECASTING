## Overview

The system uses **two database engines** side by side:

| Engine | Use | Connection |
|--------|-----|-----------|
| **PostgreSQL** (async) | Main app data — users, schedules, forecasts, metrics, audit | SQLAlchemy async via `asyncpg` |
| **SQLite** (sync) | ML engine state — TIDE bias corrector persistence | Raw `sqlite3` module |

**Total: 12 SQLAlchemy models + 1 raw SQLite table = 13 tables.**

### 10—12. `raw_data_uploads`, `validated_data`, `validation_reports` — CSV Upload Pipeline

These three tables form a data ingestion pipeline:

```
CSV Upload → raw_data_uploads (pending)
                 ↓ validation (7 physics checks)
            validation_reports (pass/fail)
                 ↓ if passed
            validated_data (clean rows)
```

**`raw_data_uploads`** — tracks every uploaded CSV file.  
**`validation_reports`** — stores pass/fail + per-check results.  
**`validated_data`** — stores the validated rows (timestamp, load, line flows, voltage, current, temp, frequency).

**Note:** This pipeline is **separate** from the ML forecasting pipeline (which uses `ecg_historical_demand`). The `validated_data` table is mostly consumed by `monthly_analyzer` and `GET /data/latest`.

**Models NOT exported** from `models/__init__.py` — imported directly by their service files.

## Key Architectural Findings

1. **Only 1 declared ForeignKey** in the entire schema: `audit_logs.schedule_id → daily_dispatch_schedules.id`. All other relationships (`hourly_demand.schedule_id`, `hourly_supply.schedule_id`) are **implicit** — no referential integrity enforcement at the database level.

2. **Two DB engines**: PostgreSQL (main app) + SQLite (ML state). The SQLite file lives at `Backend/app/models/dlinear/tide_state.db`.

3. **Unused export gap**: 4 models (`User`, `RawDataUpload`, `ValidatedData`, `ValidationReport`) are **not re-exported** from `db/models/__init__.py` — they are imported directly by their consumers.

4. **`ecg_historical_demand` is write-only from external scripts** — the API layer never inserts into it. It's the primary data source for ML forecasts.

5. **`validated_data` is mostly decoupled from production** — the forecast pipeline reads `ecg_historical_demand`, not `validated_data`. The latter serves the CSV upload validation pipeline and monthly analysis.

6. **`forecast_cache` has no TTL** — entries accumulate unboundedly until `POST /forecast/dispatch/refresh` clears the entire table.

7. **The audit hash chain** is a proper SHA-256 Merkle chain: each entry's hash depends on the previous hash, enabling full integrity verification via `verify_chain()`.
