# Backend System Architecture: FastAPI Load Forecasting API

> **Technology Stack:** FastAPI + PostgreSQL/TimescaleDB + SQLAlchemy (Async) + Redis  
> **Purpose:** Production-ready REST API for load forecasting, optimized for AI-assisted procedural building.  
> **Key Framework Choice:** **FastAPI** chosen for its high performance (async), native Python ML integration, and automatic OpenAPI documentation.

---

## Part 1: Technology Stack & Rationale

| Component | Technology | Rationale |
|-----------|-----------|-----------|
| **Primary Framework** | **FastAPI** | Async/await support, fast performance, Python-native for ML models. |
| **API Documentation** | Swagger/Redoc | Auto-generated by FastAPI, simplifies frontend-backend sync. |
| **Database (TS)** | TimescaleDB | PostgreSQL extension optimized for time-series (load data). |
| **ORM** | SQLAlchemy 2.0 | Async-first, robust type mapping for Rust-like safety in Python. |
| **Validation** | Pydantic v2 | High-speed data validation and serialization. |
| **Task Queue** | Celery / RQ | For long-running model training or batch forecasting. |
| **Deployment** | Docker Compose | Containers for API, DB, and Workers. |

## Part 3: Procedural Implementation Stages (AI-Assisted)

This project is designed to be built in stages so the AI (Warp Coder) can focus on one functional block at a time.

### Stage 1: The Skeleton (System Foundation)
**Goal:** Run a Dockerized FastAPI app with an async DB connection.
1. Create `docker-compose.yml` with FastAPI + TimescaleDB + Redis.
2. Implement `app/main.py` with basic health checks.
3. Configure `app/db/session.py` for async Postgres access.
4. **Verification:** `docker-compose up` results in accessible Swagger UI at `/docs`.

### Stage 2: Data Ingestion & Validation (The "Input")
**Goal:** Handle SCADA data uploads with physics-based validation.
1. Implement `POST /api/v1/data/upload` using `multipart/form-data`.
2. Port Phase 1 physics checks (net imbalance, sign conventions) into `services/data_validation.py`.
3. Create Pydantic schemas for data validation.
4. **Verification:** Uploading a CSV returns a validation report with flags for anomalies.

### Stage 3: Feature Engineering Service (The "Bridge")
**Goal:** Reproduce features from research scripts for live inference.
1. Port `FEATURE_ENGINEERING/feature_engineering_pipeline.py` into `services/feature_engine.py`.
2. Implement deterministic lag, rolling, and temporal feature generation.
3. **Verification:** Passing a raw 15-min window to the service returns a feature matrix compatible with the models.

### Stage 4: Short-Term Forecast (STLF) Engine
**Goal:** Implement the 1-step recursive Autoformer and direct LightGBM.
1. Implement `ml/stlf_ensemble.py` featuring the Kalman Fusion logic.
2. Add `POST /api/v1/forecast/stlf` endpoint.
3. Link the service to load `.pkl` models from a central registry.
4. **Verification:** Requesting a 24h STLF returns P50 and uncertainty bands.

### Stage 5: Long-Term Forecast (LTLF) Engine
**Goal:** Implement the "Winner" daily recursive peak model.
1. Implement `ml/ltlf_recursive.py` using the 7.14 MW MAE logic.
2. Create daily aggregation logic in the service layer.
3. Add `POST /api/v1/forecast/ltlf` for monthly peak horizons.
4. **Verification:** LTLF endpoint returns daily peak forecasts for the next 30 days.

### Stage 6: Explainability & Dashboards
**Goal:** Surface why a forecast is high/low.
1. Implement SHAP explainer endpoint `GET /api/v1/explain/{id}`.
2. Add current regime detection (Regime 0, 1, 2).
3. **Verification:** Response includes the top 3 features (e.g., "Lag_96 contribution: +12 MW").

## Part 5: Deployment Strategy

**Docker-First:**
- **Container A:** FastAPI (Web API + Background Tasks)
- **Container B:** TimescaleDB (Time-series Storage)
- **Container C:** Redis (Caching & Task Queue)

**Scalability:**
- Use **Gunicorn with Uvicorn workers** for process-level scaling.
- Mount **models/** directory via volume for easy model updates (Champion/Challenger swaps).
